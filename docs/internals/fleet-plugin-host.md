# Fleet plugin host internals

How core decides plugin state and fences work. The wire contract is
[plugins](../fleet/plugins.md); this note explains the mechanisms behind it.

## Readiness and epoch

The row described under "Stored state" is the truth; every replica's probe
writes evidence to it, and everything else reads it. Each registry entry
caches its row.

- Every replica probes each registered plugin's manifest every 1 s and writes
  the result as one of the transitions below. The first matching answer from
  any replica makes the plugin ready on all of them. The plugin's session poll
  then succeeds (it got 421 until then) and the plugin starts work under that
  epoch.
- A replica forwards public API calls and serves host requests while the
  cached row is enabled, has an epoch and an instance, this replica's own
  manifest check did not find a mismatch (T3a), and either the row's
  `seen_at` or this replica's own last good probe is under 3 s old. A plugin
  unreachable from one replica only keeps its epoch; that replica's
  forwarded calls fail with 503.
- The epoch changes on every lifecycle change (T5), plugin restart (T2),
  refusal (T3), and after 3 s in which no replica saw the plugin (T4). One
  lost probe changes nothing. A refusal rotates only an epoch that was seen,
  so a plugin that keeps refusing is fenced once, not every second.
- When a replica adopts a new epoch it cancels its admitted calls (the
  lease) and forgets its own probe result, so it never acts again on evidence
  another replica already acted on. A request with an old instance or epoch
  is refused with 421 on both sides. Work admitted before a drain, disable or
  restart cannot continue after it.
- Reading the row:

  | Path | Reads |
  | --- | --- |
  | Session route | The row from the database on every request, so every replica answers the same at once. A database error is 503 |
  | Other host requests | The cache. On an instance or epoch mismatch, the row once more, then compare again |
  | API forwarding and status | The cache. On a plugin's 421, `Registry.refresh` reads the row and core answers 503 with `Retry-After: 1` |
  | `GET /api/v1/plugins` | The cache |

- The cache is read again on the `fleet_plugin` hint (`Registry.Notify`,
  bound with `postgres.Store.SetPluginSignal`), after the listener reconnects
  (an empty hint), and by a sweep every 500 ms. Every read or write of one
  plugin's row and the adoption of its result hold that entry's row slot, so
  an older read never replaces a newer one.
- Core never forwards a plugin's 421 and never maps it to a conflict. 409
  passes through, because it always means a conflict in the plugin's own
  domain.

## Stored state

One row per plugin in `fleet.plugin_lifecycle` is the single source of its
state, so that every core replica shows the plugin one epoch (schema
migration 013). Replicas write evidence to it and read it back; nothing else
holds the epoch.

| Column | Meaning |
| --- | --- |
| `desired`, `revision` | Admin lifecycle (`enabled`, `draining`, `disabled`) and its revision, which `If-Match` checks. Revision 0 is valid: it is a row created by a probe |
| `epoch` | The plugin's one epoch, 32 lowercase hex characters, generated by core |
| `instance_id` | The plugin process the epoch was issued to; null until a probe has seen one |
| `seen_at` | Database time of the last successful manifest probe by any replica; null after a fence or lifecycle change, until the next probe |

A row is created by the first successful probe (enabled, revision 0) or the
first lifecycle change (revision 1, no instance). A plugin without a row is
enabled at revision 0, as before. At most 256 rows.

Readiness is a function of the row, in database time:
`desired = 'enabled' AND instance_id IS NOT NULL AND now() - seen_at < 3 s`.

Every change is one conditional write that names the epoch the replica read
last. When the epoch no longer matches, nothing changes and the store returns
the current row for the replica to adopt. All times are the database's; the
store returns `SeenAge` (negative when unseen) computed in SQL.

| # | A replica observes | Store call | Epoch | `seen_at` |
| --- | --- | --- | --- | --- |
| T1 | Probe ok, same instance | `SeenPlugin`; writes only when `seen_at` is null or older than 500 ms | Kept | now |
| T2 | Probe ok, another instance (or none recorded) | `SeenPlugin` | New | now |
| T3 | The plugin refused (non-200) | `FencePlugin(unseenOnly=false)` | New at once | null |
| T3a | The manifest does not match this replica's registration | No call: that replica stops forwarding and shows `incompatible` | Kept | Kept |
| T4 | No answer | `FencePlugin(unseenOnly=true)`; only when `seen_at` is set and at least 3 s old | New | null |
| T5 | Admin lifecycle call | `SetPluginLifecycle`; locks the row, needs the current revision, `revision + 1` | New | null |

- The first probe of a plugin without a row inserts it, seen now. Under
  concurrent probes one insert wins and the others adopt its row.
- T4 leaves a plugin that was never seen under the epoch alone. T3 and T5
  already cleared `seen_at`, so a second replica that also cannot reach the
  plugin finds nothing left to fence, and the epoch does not change every
  second during an outage. One lost probe changes nothing; 3 s without any
  successful probe from any replica rotates once.
- A write that changed a row sends `NOTIFY fleet_plugin, '<plugin id>'` in the
  same transaction. This includes the T1 refresh (at most about once a second
  per plugin for the whole cluster). The hint only wakes readers; the table is
  the truth.
- The memory store applies the same rules in process with an injectable
  clock (`fleet.Store.SetClock`), so memory mode now has a lifecycle store
  too; it does not survive a restart, and it checks no actor (the registry
  checks the caller's role). It sends no hint; one process needs none.
- `internal/fleet/fleettest` holds the contract suites for both stores:
  `RunPluginState`, and `RunInventory` for agent generation fencing, the
  binding of a connected UID to its credential and paging. PostgreSQL also has tests for the hints, for a probe,
  a fence and lifecycle changes racing on one row, and for the migration of
  existing rows (`scripts/fleet/test-postgres.sh`).

## Lifecycle behavior

- Admin lifecycle (`enable`, `drain`, `disable`) survives crashes, restarts
  and restores on PostgreSQL.
- The operator `enabled` ceiling is checked first: `enable` needs it.
- Plugin-state metrics and lifecycle persistence do not wait on each other;
  contended state is reported as unknown.

## Ingress

- The host listener exists only when registrations are configured.
- Each registration has its own host and service token; the host token alone
  identifies the plugin on the host listener.
- Public ingress has two read and two write slots per plugin, independent of
  manifest and status polling. Fleet reads the request body (64 KiB, 2 s
  deadline) before it takes a slot, so a slow client cannot hold one.
- Status polling has its own two slots and refuses a third call. The manifest
  probe has a dedicated slot and connection pool, so status calls cannot
  starve it and drop the plugin out of `ready`. Host services allow two
  concurrent requests per plugin, and the session route has a slot of its own
  (`entry.sessions`), so the session poll never waits for them and they never
  wait for it. The plugin side mirrors it: a dedicated HTTP client for the
  session poll, because the SDK client has two connections per host.
- Receivers ignore unknown JSON fields in both directions: the manifest and
  host answers go through `pluginsdk.RequestJSON`, and host requests through
  `decodeHost`, neither of which disallows unknown fields. The registration
  file stays strict: it is operator configuration, not protocol, and a typo
  there should fail startup.
- Session loss policy of a plugin (live capture, the example): a refusal or
  421 answer or a changed epoch ends the session at once; a timeout or
  transport error (`pluginsdk.Unreachable`) needs two polls in a row, about
  1.5 s.
- Introspection takes a token SHA-256, so Collector tokens never reach fleet
  over the host channel. Only agent credentials introspect as active.
- Core never forwards plugin traffic to Collectors and never sends commands
  for a plugin; reporting stays read-only.

## Compatibility

- Protocol `"4"` is fixed: routes, field names and bounds do not change within
  it, and fields may be added because receivers ignore unknown ones. A
  breaking change gets a new protocol version and new route prefixes. Fleet
  reports a plugin whose manifest declares another protocol as
  `incompatible`. Protocol 4 replaced 3 outright (421 for a stale instance or
  epoch, unknown fields ignored, a session slot); there is no fallback.

Test coverage for the registry and host services is in [fleet
verification](fleet-verification.md#plugins).
